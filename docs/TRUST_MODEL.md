# Dependency Zero — Trust Model

This document states what the multi-scanner and Solana layers actually
guarantee, and — more importantly — what they do not. Nothing here is a
roadmap or an aspiration; every statement describes the code as it stands.

## 1. The three scanners are one operator, not a network

Dependency Zero runs three distinct **analytical modules**:

| Role | Label | Responsibility |
|---|---|---|
| `static_lifecycle` | Static & Lifecycle Analysis | Source, install/lifecycle scripts, execution patterns, code evidence |
| `dependency_advisory` | Dependency & Advisory Analysis | Resolved identity, declared dependencies, live OSV advisories |
| `artifact_integrity` | Artifact & Integrity Analysis | Registry identity, artifact SHA-256, published integrity, archive safety |

They are **not three independent operators**. All three run in one process on
one machine, and their private keys live in one key store on that machine,
generated by it and controlled by a single party.

**What three signatures prove:**
- Every module produced a result, and that result has not been altered since.
- Every module is bound to this exact scan, this exact artifact hash, these
  exact versions, and its own findings commitment.
- A disagreement between the three is visible rather than averaged away.

**What three signatures do NOT prove:**
- That three independent parties looked at the package.
- Byzantine fault tolerance of any kind.
- That the operator is honest or has not colluded with itself.
- Decentralisation, in any sense.

The operator string carried in every registry entry is literally
`local-operator (single machine)` so this cannot be mistaken downstream.

To obtain genuine independent verification, the three roles would have to be
operated by three unrelated parties holding keys the operator cannot reach. The
protocol supports that — the registry, consensus and verification code are all
built around per-role public keys — but it has not been done, and no UI in this
product implies it has.

## 2. Solana Devnet anchoring

### What is deployed

**No on-chain program is deployed.** This environment has no Rust, no cargo, no
Solana CLI and no Anchor, so compiling and deploying a registry or attestation
program is impossible here. No Program ID is claimed anywhere, and no on-chain
registry account exists.

### What is actually used

Commitments are anchored with the well-known SPL Memo program
(`MemoSq4gqABAXKb96qnH8TysNcWxMyWCqXgDLGmfcHr`). Every attestation produced this
way is labelled exactly:

> **Solana Devnet commitment anchored via Memo**

A Memo transaction is a real, immutable, publicly verifiable Solana Devnet
transaction. It is **not** a deployed registry program, **not** a smart-contract
attestation system, and it holds no on-chain state beyond a public note.

### Memo commitment is not an on-chain registry program

These are different things and are never conflated in this codebase:

| | Memo commitment | On-chain registry program |
|---|---|---|
| What exists | A public note in a transaction | Deployed executable bytecode |
| Program ID | `MemoSq4gqABAXKb96qnH8TysNcWxMyWCqXgDLGmfcHr`, a well-known SPL program owned by nobody here | Would be Dependency Zero's own deployed program |
| Who deployed it | SPL / the Solana ecosystem | This project |
| Enforces anything | No | Would hold registry state and enforce rules |
| Present here | Yes | **No — never deployed** |

No registry or attestation program is deployed by this project. No Program ID
belonging to Dependency Zero is claimed anywhere. The registry is a local file;
the only thing that reaches the chain is a hash inside a Memo.

A proof bundle therefore carries `registry.onChainProgramDeployed: false`, and
the standalone verifier **fails** any bundle that claims otherwise.

### Memo instruction encoding: raw UTF-8, not length-prefixed

This bit us in practice and is recorded so it is not rediscovered.

The SPL Memo program used here (`MemoSq4gqABAXKb96qnH8TysNcWxMyWCqXgDLGmfcHr`,
v2) takes its instruction data as **raw UTF-8**. It does **not** use the bincode
`Memo { data: String }` form — a 4-byte little-endian `u32` length followed by
the payload — that **Memo v1** uses.

Sending the v1 form to the v2 program is rejected. The runtime decodes byte 0 of
the data as UTF-8; the length prefix for a 226-byte payload begins with `0xE2`,
which is not a valid UTF-8 lead byte, and the transaction fails:

```
InstructionError [0, "InvalidInstructionData"]
log: Program log: Invalid UTF-8, from byte 0
```

The accepted form, taken from the program's own Devnet log:

```
Program log: Memo (len 226): "D0/d0-attestation/1 | c=57a6579d... | ..."
```

Two consequences for anyone re-implementing this:

- **Encoding** is `Buffer.from(text, "utf8")` with no prefix.
- **Decoding** must not blindly strip four bytes. The decoder here accepts both
  forms, recognising the v1 prefix only when the declared length matches the
  remaining bytes exactly. A wrong decode cannot produce a false pass, because
  verification compares the parsed commitment against a hash recomputed locally.

Encoding and decoding live in `lib/attest/memo.ts`, which imports no Solana SDK,
so the application and the standalone verifier cannot drift apart on it.

### What anchoring genuinely provides

Tamper-evident timestamping. The commitment hash is bound to a specific slot in
a public ledger that no party — including this operator — can rewrite afterwards
without invalidating the transaction signature.

### What it does not provide

- Any claim of decentralisation. A Memo write is not governed by consensus rules
  relevant to package security.
- Data availability or retrievability of the underlying scan. The commitment is
  a hash; the evidence stays off-chain.
- Liveness or censorship resistance. Devnet is a test cluster with no
  availability guarantee, and a rate-limited faucet can block anchoring.

### The scanner registry

The registry is **off-chain and local**. Its entries describe keys this host
trusts. A registry commitment hash may be anchored on Devnet, which lets an
independent party confirm the trusted key set had not changed — but that is a
hash of a local list, not an on-chain registry that enforces anything.

`onChainProgramDeployed` is `false` in every proof bundle, and the standalone
verifier **fails** a bundle that claims otherwise.

## 3. The consensus clamp

The single most important safety rule:

> Consensus may be equal to or **more restrictive** than the authoritative
> security verdict. It may never be less restrictive.

This exists because of a real defect found during the `express@4.18.2` run.
Scanner B held two medium advisories (risk 18) and Scanner A one low-severity
source finding (risk 9). Each partition legitimately evaluated to ALLOW on its
own, because only the **complete** finding set crosses the review threshold of
25. Quorum therefore reported ALLOW for a package the security engine was
holding as REVIEW.

The clamp is implemented in `computeConsensus`, recorded in the consensus
rationale, and locked in by four regression tests in `tests/attest.test.ts`.

Additional consensus safety rules:

- A BLOCK vote is never outvoted into ALLOW by clean assessments.
- A missing or unavailable scanner is `unavailable`, never an approving vote.
- Any cryptographic failure prevents verified consensus entirely.
- Unknown, revoked, or role-mismatched identities are rejected, not trusted.
- Conflicting scanner versions force REVIEW rather than a blind merge.
- Quorum is required before ALLOW can stand.

## 4. Attestation is not a prerequisite for the security verdict

The security verdict and the Solana attestation have **separate lifecycles**.
An attestation runs after the verdict is already persisted. An unreachable RPC,
a rate-limited faucet, an unprovisioned signer or a missing balance can never
erase, downgrade or delay a completed security scan — it only leaves the
attestation in an honest non-confirmed state, and the UI says why.

The firewall enforcement rules are unchanged. **The CLI firewall does not
require verified consensus or chain anchoring to enforce.** It enforces the
deterministic local security verdict exactly as in Phase 1+2. Making a package
install depend on Devnet availability would turn a test cluster into a hard
dependency of local security, which would be a fail-open hazard rather than a
hardening measure. Solana is an additional, verifiable audit layer, not a gate.

## 5. Cryptographic guarantees

- Ed25519 via Node's native `crypto`. No custom curve code.
- Canonical byte encoding with fixed field order, length-prefixed strings and
  fixed-width integers, so no two distinct objects can produce the same bytes.
- A domain separator (`DEPENDENCY-ZERO/ATTESTATION`) prevents a signature for
  this protocol being replayed into another protocol.
- The signed payload binds scan id, resolved name and version, artifact SHA-256,
  scanner public key, scanner role, scanner and policy versions, findings
  commitment, proposed verdict, risk score, completion status and timestamp.
- Findings commitments sort findings before hashing, so a reordered finding list
  is the same commitment while a changed finding is a different one.
- Memo payload carries only the commitment and lookup identifiers — no package
  internals, no secrets, nothing sensitive on a permanent public ledger.

## 6. Key handling

- Private keys are generated on first use and stored **outside the repository**,
  under the OS application-data directory, `keys/scanner-identities.json`.
- The module holding them is `server-only`, so the Next.js client/server boundary
  rejects any attempt to import it from a component.
- Files are written `0600` in a `0700` directory where the platform honours it.
  Windows does not implement POSIX modes; on Windows the protection is the
  directory location plus the `server-only` boundary.
- Private keys never appear in Git, the client bundle, an HTTP response, a log
  or a proof bundle. `d0-verify` holds no secrets at all.
- The Solana attester keypair is a separate, explicitly provisioned devnet key.
  The user's Phantom wallet is never used for automated anchoring, and its seed
  phrase is never requested, read or stored.

## 7. Known limitations

- Scanner C is **not** a behavioural sandbox. It never executes package code.
  Findings are about the container and its provenance, not runtime behaviour.
- Advisory availability is best-effort per scan. When OSV is unreachable the
  check is recorded as incomplete, which forces at least REVIEW rather than
  silently reporting "clean".
- There is no revocation feed. Revocation is a local registry edit.
- There is no expiry or freshness policy on attestations.
- Signature verification proves origin, not scanner quality. A compromised
  scanner key produces valid signatures over wrong answers.
